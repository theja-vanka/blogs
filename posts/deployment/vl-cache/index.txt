<section id="sec-intro" class="level1">
<h1>The problem: KV cache is the bottleneck for long-context VLMs</h1>
<p>Vision-Language Models (VLMs) extend LLMs to accept images and video frames as additional input tokens. As VLMs are pushed to handle higher-resolution images, multiple images, and multi-frame video, the number of <strong>visual tokens</strong> in the prompt grows quickly — and each of those tokens needs a cached key/value (KV) pair at every transformer layer once it has been processed.</p>
<p>Recall how autoregressive transformer inference works:</p>
<ul>
<li>In the <strong>prefill</strong> phase, all <code>m</code> prompt tokens (visual + language) are processed in parallel, and their per-layer key/value vectors are cached in GPU memory.</li>
<li>In the <strong>decoding</strong> phase, the model generates one token at a time; each new token’s key/value vectors are appended to the cache so they don’t need to be recomputed at the next step.</li>
</ul>
<p>The problem is that this KV cache is <strong>read from and written to GPU high-bandwidth memory (HBM) at every single decoding step</strong>, and its size grows linearly with context length. The paper gives a concrete example: with a batch of 4 prompts, 5 images per prompt, and 2K visual tokens per image, serving <strong>LLaVA-1.6-34B requires 110 GB of HBM just for the visual-token KV cache</strong>. That is a huge, mostly-fixed tax paid on every decoding step regardless of how much of that cached information the model actually uses.</p>
<section id="why-vlm-attention-is-not-like-llm-attention" class="level2">
<h2 class="anchored" data-anchor-id="why-vlm-attention-is-not-like-llm-attention" id="why-vlm-attention-is-not-like-llm-attention">Why VLM attention is <em>not</em> like LLM attention</h2>
<p>Prior KV-cache-compression work (StreamingLLM, H2O, PyramidKV, …) was designed for text-only LLMs and simply evicts “unimportant” cache tokens based on attention scores. The authors show this transfers poorly to VLMs because <strong>VLM attention has a structurally different shape</strong>: there is a sharp <em>modality boundary</em> between visual tokens and the language tokens that follow them.</p>

<p><strong>Figure 1</strong> (reproduced above from the paper). Darker red = higher attention score. Both matrices show that the tokens that matter during decoding are largely the same ones that mattered during prefill — which is <em>why</em> KV cache compression is possible at all. The key difference in panel (b) is the <strong>clear modality boundary along the query dimension</strong>: language tokens attend strongly to the language tokens that come right after the image (the “post-vision” tokens), not diffusely across all preceding visual tokens. This single observation motivates the entire method.</p>
<p>Because prior methods are <em>modality-unaware</em>, they conflate attention mass coming from visual tokens with attention mass coming from language tokens, which — as the paper demonstrates empirically in its accuracy benchmarks (<a href="#sec-accuracy" class="quarto-xref">Section&nbsp;6.2</a>) — leads to suboptimal token eviction decisions for VLMs.</p>
</section>
<section id="two-more-empirical-observations-that-shape-the-method" class="level2">
<h2 class="anchored" data-anchor-id="two-more-empirical-observations-that-shape-the-method" id="two-more-empirical-observations-that-shape-the-method">Two more empirical observations that shape the method</h2>
<ol type="1">
<li><strong>Attention sparsity varies a lot across layers.</strong> Measured sparsity ranges from <strong>70% to 99%</strong> across transformer layers, with the first couple of layers noticeably denser than the rest. Prior work allocates the same cache budget to every layer (H2O, Keyformer) or a fixed monotonically-decreasing schedule (PyramidKV, PyramidInfer) — both of which under-fit this per-layer variation.</li>
<li><strong>Sparsity also differs between visual and language tokens</strong>, and depends on the specific prompt, so a <em>fixed</em>, prompt-independent budget schedule can’t be optimal — the budget really needs to be computed <strong>per prompt, at inference time</strong>.</li>
</ol>
</section>
<section id="contributions-restated" class="level2">
<h2 class="anchored" data-anchor-id="contributions-restated" id="contributions-restated">Contributions, restated</h2>
<ol type="1">
<li><strong>A characterization of VLM attention sparsity</strong> across the prefill and decoding phases, showing it’s structurally different from LLM attention.</li>
<li><strong>Layer-adaptive, sparsity-aware KV cache budget allocation</strong> — how much cache each layer gets is computed dynamically from that layer’s own measured sparsity, not from a fixed schedule.</li>
<li><strong>A modality-aware token scoring policy</strong> (“Accumulated Post-vision Attention”) that uses language-to-vision attention as a robust signal for which tokens (visual <em>and</em> language) are worth keeping.</li>
</ol>
</section>
</section>
<section id="sec-background" class="level1">
<h1>Background</h1>
<section id="vlm-inference-prefill-and-decoding" class="level2">
<h2 class="anchored" data-anchor-id="vlm-inference-prefill-and-decoding" id="vlm-inference-prefill-and-decoding">VLM inference: prefill and decoding</h2>
<p>Let a VLM prompt be a sequence of <code>m</code> tokens (mixing visual and language tokens after the visual encoder + projection layer have turned image patches into “soft prompt” embeddings): <span class="math inline">\(\{x_1, \dots, x_m\}\)</span>.</p>
<p><strong>Prefill phase.</strong> All <code>m</code> tokens are processed in parallel to compute <span class="math inline">\(P_\theta(x_{m+1} \mid x_1, \dots, x_m)\)</span> — the probability distribution for the first generated token. While doing this, the model caches the per-layer key and value vectors <span class="math inline">\(\{k_1^{(l)}, \dots, k_m^{(l)}\}\)</span> and <span class="math inline">\(\{v_1^{(l)}, \dots, v_m^{(l)}\}\)</span> for every transformer layer <span class="math inline">\(l\)</span>, so they don’t need to be recomputed later.</p>
<p><strong>Decoding phase.</strong> At step <span class="math inline">\(i\)</span>, the model consumes token <span class="math inline">\(x_{m+i}\)</span> and computes <span class="math inline">\(P_\theta(x_{m+i+1} \mid x_1, \dots, x_{m+i})\)</span>. This produces new key/value vectors <span class="math inline">\(k_{m+i}^{(l)}\)</span>, <span class="math inline">\(v_{m+i}^{(l)}\)</span> per layer, which get appended to the running cache. As context length grows (many images, video, or long generations), the <strong>KV cache can exceed the size of the model’s own parameters</strong>, making memory capacity and bandwidth — not compute — the bottleneck.</p>
</section>
<section id="kv-cache-compression-two-independent-design-axes" class="level2">
<h2 class="anchored" data-anchor-id="kv-cache-compression-two-independent-design-axes" id="kv-cache-compression-two-independent-design-axes">KV cache compression: two independent design axes</h2>
<p>The paper frames KV cache compression as having exactly two design dimensions, and this framing is the backbone of the whole method:</p>
<ol type="1">
<li><strong>Budget allocation</strong> — <em>how many</em> cache slots does each layer get?
<ul>
<li>Naïve baseline: equal budget per layer (used by StreamingLLM, H2O).</li>
<li>PyramidKV / PyramidInfer: a fixed, monotonically decreasing budget with depth (more budget to shallow layers, less to deep ones), motivated by the empirical finding that evicting cache at different layers hurts accuracy by different amounts.</li>
</ul></li>
<li><strong>Token scoring policy</strong> — <em>which</em> tokens within a layer’s budget get kept?
<ul>
<li>Formally: given <code>n</code> cached tokens at layer <code>l</code> indexed by <span class="math inline">\(S = \{0, \dots, n\}\)</span>, a scoring policy is a function <span class="math inline">\(\psi: S \to \mathbb{R}^n\)</span>. Given a budget <span class="math inline">\(k \in [1, n)\)</span>, the tokens kept are the top-<code>k</code> scorers: <span class="math display">\[S_\psi := \{i_1, i_2, \dots, i_k : \psi(S)_{i_j} \ge \psi(S)_{x \in [n]\setminus\{i_1,\dots,i_k\}}\}\]</span></li>
<li>StreamingLLM keeps only the earliest (“attention sink”) tokens plus the most recent ones.</li>
<li>H2O uses <strong>accumulated attention scores</strong> (summed over the query dimension) to keep “heavy hitter” tokens.</li>
</ul></li>
</ol>
<p>The paper’s unifying insight: KV cache compression only works <em>because</em> transformer attention is sparse in the first place — so both budget allocation and token scoring should be driven by <strong>measured sparsity</strong>, not fixed heuristics. That idea is developed in the next section.</p>
</section>
</section>
<section id="sec-prelim" class="level1">
<h1>Preliminary experiments: measuring VLM attention</h1>
<p>Before designing the algorithm, the authors run a diagnostic study. They sample prompts from three datasets — <strong>DocVQA</strong> (OCR/document QA), <strong>MathVista</strong> (visual math reasoning), and <strong>Coco-Caption</strong> (captioning, i.e.&nbsp;world knowledge) — feed them through <strong>LLaVA-Mistral-7B</strong>, and record the full attention score matrices through generation.</p>
<section id="sec-sparsity" class="level2">
<h2 class="anchored" data-anchor-id="sec-sparsity" id="sec-sparsity">Measuring attention sparsity</h2>
<p>To measure sparsity cheaply (it needs to run <em>at inference time</em>, not just for offline analysis), the paper defines a fast relative-threshold filter instead of using top-<code>k</code>/top-<code>p</code> truncation (which would require sorting):</p>
<p><span class="math display">\[
\text{ThresholdFilter}(A, p)_{ij} =
\begin{cases}
A_{ij} &amp; \text{if } A_{ij} \ge p \cdot \max_j(A_{ij}) \\
0 &amp; \text{otherwise}
\end{cases}
\qquad (1)
\]</span></p>
<p>with <span class="math inline">\(p \in (0,1)\)</span> heuristically set to <strong>1%</strong> (small enough that the filtered-out scores barely affect the layer’s output). <code>ThresholdFilter</code> is asymptotically faster than top-<code>p</code>/top-<code>k</code> truncation because it doesn’t require sorting the attention distribution.</p>
<p>Given the filtered matrix, per-layer sparsity <span class="math inline">\(\gamma^{(l)} \in [0,1]\)</span> is the fraction of zero entries in the <strong>lower-triangular</strong> (causal) portion of the attention matrix:</p>
<p><span class="math display">\[
\gamma^{(l)} := \frac{\sum_{i \ge j} \mathbb{1}[\text{ThresholdFilter}(A^{(l)}, p)_{ij} = 0]}{|\{A_{ij}^{(l)} : i \ge j\}|}
\qquad (2)
\]</span></p>

<p>Findings from this experiment:</p>
<ul>
<li>Sparsity ranges from about <strong>70% to 99%</strong> across layers — this is <em>not</em> uniform, contradicting the equal-budget assumption used by H2O/Keyformer.</li>
<li>The <strong>first two layers</strong> are noticeably less sparse (denser, more “important” in the sense of needing more cache) than the rest, and a few <strong>middle layers</strong> are also denser than their neighbors — this non-monotonic pattern contradicts the <em>monotonically decreasing</em> schedule used by PyramidKV/PyramidInfer.</li>
<li>The decoding-phase sparsity curve (b) closely tracks the prefill-phase curve (a), except the 2nd layer becomes much sparser during decoding. The <strong>Pearson correlation coefficient</strong> between the prefill and decoding sparsity curves (averaged across layers) is <strong>0.695</strong> — high enough that the authors conclude prefill-phase sparsity can be used to <em>predict</em> how much cache a layer will need during decoding.</li>
</ul>
<p>This last point is the linchpin of the method: <strong>you can measure sparsity once, cheaply, right after prefill, and use it to decide the decoding-phase cache budget</strong> — no need to observe decoding attention at all (which wouldn’t be available yet anyway).</p>
</section>
<section id="sec-hitrate" class="level2">
<h2 class="anchored" data-anchor-id="sec-hitrate" id="sec-hitrate">Measuring cache hit rate and the “post-vision” hypothesis</h2>
<p>Going back to the modality boundary observed in Figure 1(b), the authors hypothesize that scoring cache tokens by their attention <em>from the post-vision language tokens</em> (rather than from the <em>whole</em> prompt) will more faithfully identify which tokens the model actually needs during decoding.</p>
<p>To test this rigorously, they define an oracle-relative metric.</p>
<div class="callout callout-style-default callout-note callout-titled">
<div class="callout-header d-flex align-content-center" data-bs-toggle="collapse" data-bs-target=".callout-2-contents" aria-controls="callout-2" aria-expanded="true" aria-label="Toggle callout">
<div class="callout-icon-container">
<i class="callout-icon"></i>
</div>
<div class="callout-title-container flex-fill">
<span class="screen-reader-only">Note</span>Definition 3.1 — CacheHitRate
</div>
<div class="callout-btn-toggle d-inline-block border-0 py-1 ps-1 pe-0 float-end"><i class="callout-toggle"></i></div>
</div>
<div id="callout-2" class="callout-2-contents callout-collapse collapse show">
<div class="callout-body-container callout-body">
<p>Let <span class="math inline">\(m\)</span> be the prompt length, <span class="math inline">\(Q_{:m}, K_{:m} \in \mathbb{R}^{m \times d}\)</span> the query/key matrices, and <span class="math inline">\(Q_{m+1} \in \mathbb{R}^d\)</span> the query vector of the <strong>first decoded token</strong>. Define the <em>true</em> decoding-time attention distribution:</p>
<p><span class="math display">\[A_{m+1} := \text{softmax}\!\left(\frac{Q_{m+1} K_{:m}^T}{\sqrt d}\right) \in \mathbb{R}^m\]</span></p>
<ul>
<li><span class="math inline">\(\psi^*: S \to A_{m+1}\)</span> — the <strong>optimal</strong> scoring function (uses the real decoding attention — only observable in hindsight).</li>
<li><span class="math inline">\(S_{\psi^*}\)</span> — the top-<code>k</code> tokens under <span class="math inline">\(\psi^*\)</span> (optimal for any budget <code>k</code>).</li>
<li><strong>CacheHitRate</strong> <span class="math inline">\(:= \dfrac{|S_\psi \cap S_{\psi^*}|}{|S_{\psi^*}|}\)</span> — the fraction of the <em>true</em> important tokens that a <em>practical</em> (prefill-only) policy <span class="math inline">\(\psi\)</span> actually manages to keep.</li>
</ul>
</div>
</div>
</div>
<p>Since <span class="math inline">\(A_{m+1}\)</span> is only known <em>after</em> decoding starts — and the entire point of compression is to shrink the cache <em>before</em> decoding — multiple prefill-time approximations <span class="math inline">\(\psi\)</span> have been proposed:</p>
<table class="caption-top table">
<colgroup>
<col style="width: 33%">
<col style="width: 33%">
<col style="width: 33%">
</colgroup>
<thead>
<tr class="header">
<th>Policy</th>
<th>Definition</th>
<th>Idea</th>
</tr>
</thead>
<tbody>
<tr class="odd">
<td><strong>Accumulated Attention</strong> (prior work, e.g.&nbsp;H2O)</td>
<td><span class="math inline">\(\psi(S) := \sum_i \text{softmax}\!\left(\frac{Q_{:m}K_{:m}^T}{\sqrt d}\right)_i\)</span></td>
<td>Sum attention over the <em>entire</em> query dimension.</td>
</tr>
<tr class="even">
<td><strong>Accumulated Sliding Window Attention</strong> (prior work)</td>
<td><span class="math inline">\(\psi(S) := \sum_i \text{softmax}\!\left(\frac{Q_{m-w:m}K_{m-w:m}^T}{\sqrt d}\right)_i\)</span></td>
<td>Sum only over a fixed-size recent window <span class="math inline">\(w\)</span>.</td>
</tr>
<tr class="odd">
<td><strong>Accumulated Post-vision Attention</strong> (this paper)</td>
<td><span class="math inline">\(\psi(S) := \sum_i \text{softmax}\!\left(\frac{Q_{m-\tau:m}K_{m-\tau:m}^T}{\sqrt d}\right)_i\)</span></td>
<td>Sum only over the <span class="math inline">\(\tau\)</span> language tokens that follow the vision tokens in the prompt.</td>
</tr>
</tbody>
</table>
<p><code>τ</code> is the count of language tokens that follow the vision tokens in the prompt — so <strong>Accumulated Post-vision Attention is a dynamic, prompt-dependent sliding window</strong>, where the window size is exactly the length of the post-vision language prompt, instead of a fixed, hand-tuned <code>w</code>.</p>
<div class="quarto-figure quarto-figure-center">
<figure class="figure">
<p><img src="/blogs/posts/deployment/vl-cache/fig3_cache_hit_rate.png" class="img-fluid figure-img" alt="VL-Cache: A Technical Walkthrough"></p>
<figcaption>Figure 3 (reproduced from the paper). Accumulated Post-vision Attention (red) achieves a consistently higher CacheHitRate across almost all layers than plain Accumulated Attention (blue) and the fixed sliding window variant (green).</figcaption>
</figure>
</div>
<p><strong>Why does plain Accumulated Attention do worse?</strong> Summing over the <em>entire</em> query dimension unavoidably gives high scores to early tokens simply because more queries have had the chance to attend to them — a length bias. A sliding window helps, but a <em>fixed</em> window size is a blunt instrument: it can be too large or too small depending on how long the post-vision prompt happens to be for a given input. Post-vision Attention sidesteps this by letting the “window” be exactly the post-vision language span, which is exactly where the modality boundary in Figure 1(b) shows the useful signal concentrating.</p>
</section>
</section>
<section id="sec-method" class="level1">
<h1>The VL-Cache method</h1>
<p>VL-Cache combines the two findings above into a two-stage recipe that runs almost entirely during the <strong>prefill</strong> phase (so its cost is a one-time overhead amortized over many decoding steps):</p>
<ol type="1">
<li>Use Post-vision Attention to compute <strong>per-layer sparsity</strong>, and turn that into a <strong>per-layer cache budget</strong>.</li>
<li>Use the <em>same</em> Post-vision Attention matrix to <strong>score and keep the top-<code>k</code> tokens</strong> within each layer’s allotted budget.</li>
</ol>
<p>The paper denotes the Post-vision Attention matrix <span class="math inline">\(A'\)</span> for brevity throughout this section.</p>

<section id="sec-budget" class="level2">
<h2 class="anchored" data-anchor-id="sec-budget" id="sec-budget">Sparsity-aware KV cache budget allocation</h2>
<p>Two steps happen once, right after prefill:</p>
<ol type="1">
<li>Apply <code>ThresholdFilter</code> (with <span class="math inline">\(p = 1\%\)</span>) to the Post-vision Attention scores <span class="math inline">\(A'\)</span> and compute layer-wise sparsity <span class="math inline">\(\gamma'^{(l)}\)</span> (same recipe as Eq. 1–2, but restricted to the post-vision query rows).</li>
<li>Given a <strong>global</strong> target cache budget <span class="math inline">\(\alpha\)</span> (a hyperparameter — e.g.&nbsp;<span class="math inline">\(\alpha = 10\%\)</span> means “keep 10% of the KV cache overall”), <strong>distribute</strong> that budget across layers in proportion to each layer’s <em>density</em> (i.e.&nbsp;<span class="math inline">\(1 - \gamma'^{(l)}\)</span>): sparser layers get less cache, denser layers get more.</li>
</ol>

         ─────────────────────────────────────────────
                    |{A'_ij : i+m-τ ≥ j}|

<p><strong>Key contrast with PyramidKV:</strong> PyramidKV uses one <strong>fixed</strong> monotonically-decreasing budget schedule for <em>every</em> prompt. VL-Cache’s <span class="math inline">\(\beta^{(l)}\)</span> is <strong>recomputed per prompt</strong> from that prompt’s own measured sparsity pattern — so a document-heavy prompt and a short-caption prompt get <em>different</em> per-layer allocations, instead of being forced into the same static shape. Note the allocation is only computed once, immediately after prefill, so its cost is amortized over the (potentially many) subsequent decoding steps.</p>

<section id="sec-scoring" class="level2">
<h2 class="anchored" data-anchor-id="sec-scoring" id="sec-scoring">Modality-aware token scoring policy</h2>
<p>Once each layer knows its budget <span class="math inline">\(k^{(l)}\)</span> (the token count implied by <span class="math inline">\(\beta^{(l)}\)</span>), VL-Cache still needs to decide <strong>which</strong> <span class="math inline">\(k^{(l)}\)</span> tokens to keep. It reuses the same Post-vision Attention matrix <span class="math inline">\(A'\)</span> (Accumulated Post-vision Attention from <a href="#sec-hitrate" class="quarto-xref">Section&nbsp;4.2</a>) as the scoring function.</p>
<p>Two advantages are argued for reusing Post-vision Attention here, rather than the full attention matrix used by prior work (e.g.&nbsp;H2O):</p>
<ol type="1">
<li><strong>Efficiency.</strong> Computing layer-wise sparsity/scores from Post-vision Attention costs <span class="math inline">\(O(\tau m)\)</span> instead of <span class="math inline">\(O(m^2)\)</span> for the full attention matrix — because <span class="math inline">\(\tau \ll m\)</span> for realistic vision-language prompts (the post-vision instruction/question is typically much shorter than the full prompt, which is dominated by visual tokens).</li>
<li><strong>Better token preservation.</strong> As shown empirically in Figure 3 (<a href="#sec-hitrate" class="quarto-xref">Section&nbsp;4.2</a>), Post-vision Attention achieves a higher CacheHitRate than plain Accumulated Attention or a fixed sliding window, i.e.&nbsp;it more reliably keeps the tokens that the model will actually attend to during decoding.</li>
</ol>
<p>The narrative tying it together: plain Accumulated Attention over-weights early tokens (length bias); a fixed sliding window helps but its size is a poorly-chosen constant across very different prompts; Post-vision Attention is a <strong>prompt-adaptive</strong> sliding window whose size is <em>derived from the prompt’s own structure</em> (the post-vision span), which is exactly where the paper’s Figure 1(b) modality-boundary observation says the useful signal lives.</p>
</section>
</section>

<p><strong>Reading the results:</strong></p>
<ul>
<li><strong>Coco-Caption:</strong> all baselines are fine once the budget exceeds ~40%, but degrade sharply below that. VL-Cache is the standout at the low end — <strong>5–10% budget is already comparable to a full cache</strong>. H2O and StreamingLLM (equal budget per layer) miss important tokens in dense layers while wasting budget in sparse ones; PyramidKV’s fixed monotonic schedule is “ineffective for all input queries” per the authors.</li>
<li><strong>DocVQA:</strong> PyramidKV is the strongest baseline here, but VL-Cache still consistently comes out ahead across the whole budget range. H2O and StreamingLLM again lack robustness as the budget shrinks.</li>
<li><strong>MathVista:</strong> differences are smaller in absolute terms (the task appears less sensitive to cache budget generally) but VL-Cache remains competitive to best-in-class across budgets.</li>
</ul>

<p><strong>How to read these numbers:</strong></p>
<ul>
<li><strong>Prefill is barely affected</strong> (speedup ≈ 0.96–0.99, i.e.&nbsp;essentially neutral, occasionally a hair slower) — this is expected, since the extra attention-statistics computation is small and happens only once per request; Appendix A.4 shows it’s just 1–6% overhead on top of prefill latency, shrinking further as prompts get longer.</li>
<li><strong>Decoding speedup grows with prompt length</strong>, reaching <strong>7.08×</strong> at 128K tokens/batch 1 — because that’s exactly where a smaller KV cache saves the most HBM traffic per decoding step.</li>
<li><strong>End-to-end speedup is bounded above by decoding speedup</strong>, since prefill is unaffected. At 128K tokens/batch 1, decoding is 7.08× faster, but prefill still eats 53% of total latency, so the blended end-to-end number comes out to only 1.66×. As the number of <em>output</em> tokens generated grows, end-to-end speedup asymptotically approaches the decoding speedup — meaning <strong>VL-Cache is most valuable for long-output tasks</strong>: captioning, video description, chain-of-thought multi-modal reasoning, etc.</li>
<li>Because batch size in this setup is capped by <em>peak prefill memory</em>, not KV cache size, compression here doesn’t directly raise the maximum batch size — the authors note that continuous batching / chunked prefill (future work) would let KV-cache size become the binding constraint, at which point VL-Cache’s memory savings would translate into higher concurrency too.</li>
<li>Figure 6 shows the practical payoff for a server operator: at any given target latency, VL-Cache serves noticeably higher throughput than the full-cache baseline, and vice versa — for the same throughput target, requests see lower latency.</li>
</ul>
</section>
</section>
<section id="sec-conclusion" class="level1">
<h1>Conclusion</h1>
<p>VL-Cache is a KV-cache compression method purpose-built for VLMs, built on two empirical observations: (1) attention sparsity varies substantially and non-monotonically across transformer layers, and this can be measured cheaply during prefill and used to predict decoding-time cache needs; and (2) VLM attention has a modality boundary, and language-to-post-vision attention is a robust, efficient signal for scoring token importance for <em>both</em> visual and language tokens. Combining a <strong>sparsity-aware, per-prompt, per-layer budget allocation</strong> with a <strong>modality-aware (“Accumulated Post-vision Attention”) token scoring policy</strong>, VL-Cache retains accuracy comparable to a full KV cache while keeping only <strong>10%</strong> of it, and delivers up to <strong>2.33×</strong> end-to-end and <strong>7.08×</strong> decoding speedups.</p>

<section id="sec-implementation" class="level2">
<h2 class="anchored" data-anchor-id="sec-implementation" id="sec-implementation">A.3 — Efficient implementation (Triton kernels)</h2>
<p>To find low-attention tokens during prefill without blowing the latency/memory budget, VL-Cache needs two statistics computed from the (potentially huge) attention score matrix:</p>
<ol type="1">
<li>The <strong>average attention score per token</strong> in the key dimension (used for token scoring).</li>
<li>The <strong>count of attention scores below <code>p</code>% of the row maximum</strong>, in the query dimension (used for the sparsity ratio, per Eq. 1–2).</li>
</ol>
<p>The catch: modern fused-attention kernels like FlashAttention and PagedAttention deliberately <strong>never materialize the full attention score matrix in HBM</strong> (that’s exactly what makes them fast). So VL-Cache needs a <em>new</em>, similarly memory-efficient kernel that computes these two statistics <em>without</em> ever writing the full attention matrix back to HBM. The design constraints, verbatim from the paper:</p>
<ol type="1">
<li>The attention mask is not written to HBM.</li>
<li>The <span class="math inline">\(QK^T\)</span> product is not written to HBM.</li>
<li>The attention scores are not written to HBM.</li>
<li>Similarly-parallelized elementwise operations (e.g.&nbsp;division, addition) are fused to avoid intermediate tensors in HBM.</li>
</ol>
<p>Their first attempt — <code>torch.compile</code> with the Triton backend — satisfied constraints (1), (3), and (4), but <em>not</em> (2): it could not automatically discover the fused matmul+softmax trick that FlashAttention uses (partitioning work along the Q dimension, keeping one Q tile resident in SRAM, and streaming K/V tiles through it while running an <em>online softmax</em>). So they hand-wrote the fused kernel in Triton.</p>
<p>The wrinkle for the <em>second</em> statistic (average attention per token in the <strong>K</strong> dimension) is that it requires reducing over the <strong>query</strong> dimension — the opposite axis from what the fused matmul+softmax kernel already partitions over. That forces a <strong>second kernel</strong>, partitioned over K instead of Q, which has to <em>recompute</em> softmax (since the scores were never stored) — but it can reuse the row-wise max/sum tensors the first kernel already computed and stored (both only <span class="math inline">\(O(Q)\)</span> in size, so cheap to keep in HBM).</p>
<div class="cell" data-eval="true" data-layout-align="center">
<div class="cell-output-display">
<div>
<p></p><figure class="figure"><p></p>
<div>
<pre class="mermaid mermaid-js">flowchart TD
    IN["Q, K in HBM"] --&gt; K1["Kernel 1 — Softmax + row-wise stats&lt;br/&gt;(reduction over K dim, Q-dim partitioned, online softmax)&lt;br/&gt;• pre-exp max over K (numerical stability)&lt;br/&gt;• post-exp sum over K (softmax normalizer)"]
    K1 --&gt;|"pre-exp max, post-exp sum&lt;br/&gt;(both O(Q), written to HBM)"| K2["Kernel 2 — Softmax + column-wise stats&lt;br/&gt;(reduction over Q dim, K-dim partitioned;&lt;br/&gt;re-derives softmax from Kernel 1's stats)&lt;br/&gt;• post-softmax sum over Q → avg. attention/token&lt;br/&gt;• count of scores below p·max over Q → sparse count"]
    K2 --&gt;|"partial sparse-count per thread block"| K3["Kernel 3 — Sum reduction&lt;br/&gt;of partial sparse counts"]
    K3 --&gt; OUT["Attention statistics:&lt;br/&gt;avg. attention score / token (scoring)&lt;br/&gt;+ per-layer sparsity ratio (budget allocation)"]

<p>The authors report that each of their two hand-written Triton kernels has roughly the same latency as a FlashAttention kernel — evidence that the 3-kernel partitioning is close to optimal for this problem. Given that overhead, they note the practical need to keep the number of <em>query</em> tokens used for statistics small (their benchmark uses only the <strong>last 50 tokens</strong> of the prompt).</p>

<section id="sec-appendix-a5" class="level2">
<h2 class="anchored" data-anchor-id="sec-appendix-a5" id="sec-appendix-a5">A.5 — Measuring attention to visual vs.&nbsp;language tokens</h2>
<p>Beyond raw sparsity, the authors quantify <em>how much</em> of a layer’s attention “budget” goes to visual tokens vs.&nbsp;language tokens, using two complementary metrics.</p>
<p><strong>Contribution</strong> measures each modality’s share of the <em>filtered</em> (sparsified) attention mass. Let <span class="math inline">\(T\)</span> be the current sequence length, <span class="math inline">\(t\)</span> the index of the first decoded token, and <span class="math inline">\(A^{(l)} \in \mathbb{R}^{T \times T}\)</span> the attention matrix at layer <span class="math inline">\(l\)</span> for one head:</p>
<p><span class="math display">\[
\text{Contribution}^{(l)}_{mod} := \frac{1}{T - t + 1} \sum_{i \ge t} \frac{\sum_{j \in J_{mod}} \text{ThresholdFilter}(A^{(l)}, p)_{ij}}{\sum_{j \in J_{all}} \text{ThresholdFilter}(A^{(l)}, p)_{ij}}
\qquad (3)
\]</span></p>
<p>where <span class="math inline">\(J_{mod}\)</span> and <span class="math inline">\(J_{all}\)</span> index one specific modality (vision or language) and all modalities respectively.</p>
<div class="quarto-figure quarto-figure-center">
<figure class="figure">
<p><img src="/blogs/posts/deployment/vl-cache/fig8_contribution.png" class="img-fluid figure-img" alt="VL-Cache: A Technical Walkthrough"></p>
<figcaption>Figure 8 (reproduced from the paper): average Contribution per layer during decoding. Visual tokens (red) dominate in layer 1, contributions are roughly comparable in layer 2, and from layer 3 onward language tokens dominate — with a mild visual-contribution bump through the middle layers.</figcaption>
</figure>
</div>
<p><strong>Coverage</strong> instead measures each modality’s share of the tokens that <em>survive</em> a hard top-<code>k</code> cache-eviction cutoff (rather than share of raw attention mass):</p>
<p><span class="math display">\[
\text{Coverage}^{(l)}_{mod} := \frac{1}{T - t + 1} \sum_{i \ge t} \frac{\sum_{j \in J_{mod}} \text{TopK}(A^{(l)}, k)_{ij}}{\sum_{j \in J_{all}} \text{TopK}(A^{(l)}, k)_{ij}}
\qquad (4)
\]</span></p>
<p><span class="math display">\[
\text{TopK}(A, k)_{ij} = \mathbb{1}\!\left[A_{ij} \in \{A_i^{(r-k+1)}, A_i^{(r-k+2)}, \dots, A_i^{(r)}\}\right]
\qquad (5)
\]</span></p>
<p>Here <span class="math inline">\(k := \lfloor \alpha \cdot T \rfloor\)</span>, <span class="math inline">\(r\)</span> is the number of columns of <span class="math inline">\(A\)</span>, and <span class="math inline">\(A_i^{(n)}\)</span> denotes the <span class="math inline">\(n\)</span>-th order statistic (rank) of row <span class="math inline">\(i\)</span> — i.e.&nbsp;<span class="math inline">\(\text{TopK}\)</span> is an indicator for “this score is among the top-<code>k</code> in its row.”</p>
<div class="quarto-figure quarto-figure-center">
<figure class="figure">
<p><img src="/blogs/posts/deployment/vl-cache/fig9_coverage.png" class="img-fluid figure-img" alt="VL-Cache: A Technical Walkthrough"></p>
<figcaption>Figure 9 (reproduced from the paper): average Coverage per layer at α = 10% cache budget. The overall trend matches Contribution (Figure 8), but visual tokens claim a <em>larger share of surviving tokens</em> than their share of raw attention mass in the middle layers — meaning each individual surviving visual token, on average, contributes less attention than each surviving language token there.</figcaption>
</figure>
</div>
<p><strong>Why this matters for the method:</strong> because the vision/language attention split itself varies by layer (heavy vision in layer 1, heavy language from layer 3 onward, with a middle-layer bump in visual importance), the <em>optimal</em> per-layer budget plausibly also depends on the ratio of visual to language tokens in a given prompt. Static, pyramid-style schedules can’t adapt to that; VL-Cache’s per-prompt, per-layer, sparsity-derived allocation can.</p>

<section id="key-takeaways" class="level1">
<h1>Key takeaways</h1>
<ul>
<li>VLM attention is <strong>not</strong> a bigger version of LLM attention: it has a hard <strong>modality boundary</strong>, and the useful cache-eviction signal concentrates in the language tokens right after the image (<strong>“post-vision” tokens</strong>), not in the visual tokens themselves or in a generic recency window.</li>
<li>Attention sparsity varies <strong>70–99%</strong> across layers, non-monotonically, and prefill-phase sparsity <strong>predicts</strong> decoding-phase cache needs (Pearson <span class="math inline">\(r = 0.695\)</span>) — so budget allocation can be computed once, per-prompt, right after prefill, cheaply.</li>
<li>VL-Cache = <strong>(1)</strong> sparsity-derived, per-layer, per-prompt cache <strong>budget allocation</strong> + <strong>(2)</strong> <strong>Accumulated Post-vision Attention</strong> as the token scoring policy — both reuse the same <span class="math inline">\(O(\tau m)\)</span> Post-vision Attention computation, avoiding the <span class="math inline">\(O(m^2)\)</span> cost of full attention.</li>
<li>Empirically: <strong>10% KV cache ≈ full-cache accuracy</strong> on Coco-Caption / DocVQA / MathVista across two LLaVA backbones, beating StreamingLLM, H2O, and PyramidKV, especially at aggressive (≤10%) budgets.</li>
<li>Speed payoff: <strong>≈7×</strong> decoding speedup at 128K context, <strong>≈2.3×</strong> end-to-end speedup at high batch size, <strong>90%</strong> less KV-cache GPU memory, with only <strong>1–6%</strong> prefill overhead — the benefit is largest for <strong>long-output</strong> tasks (captioning, video description, multi-modal chain-of-thought), since end-to-end speedup approaches decoding speedup as output length grows.</li>
</ul>
